# SecureVote — Security Analysis and Threat Model

> Educational prototype. **No professional security audit has been performed.** The analysis below was written by the project team with AI assistance and is verified only by the automated tests listed in each section. Do not use the system for real elections, real funds or real personal data.

## 1. Scope and security goals

| Goal                                  | Meaning in SecureVote                                         | Primary enforcement                                          |
| ------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------ |
| **Eligibility**                       | Only registered voters of a session can vote in it            | Contract (`castVote` → `NotEligible`) + API visibility rules |
| **One vote per voter**                | A wallet can vote at most once per session                    | Contract (`hasVoted` → `AlreadyVoted`)                       |
| **Integrity of counting**             | Totals equal the sum of accepted votes × registered weights   | Contract storage; independent event recount (auditor page)   |
| **Rule immutability**                 | Options, schedule, quorum, voters cannot change after opening | Contract state machine (`Created → Open → Closed`)           |
| **Authorization**                     | Each role can only perform its own actions                    | Contract roles + server-side RBAC                            |
| **Auditability**                      | Every lifecycle step is reconstructible                       | Contract events + application audit log + tx references      |
| **Confidentiality of off-chain data** | Names, e-mails, passwords never reach the chain or logs       | Off-chain DB, hashed passwords, no-body logging              |

**Explicit non-goals of this prototype:** ballot secrecy, anonymity, coercion resistance, legal validity, high availability.

## 2. Privacy: what the prototype does and does not provide

| Property                                   | Definition                                                           | Status in SecureVote                                                                                                                                                                                      |
| ------------------------------------------ | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Public auditability**                    | Anyone with chain access can verify that counting followed the rules | ✅ Provided — every registration and vote is a public event; totals can be recomputed.                                                                                                                    |
| **Voter eligibility**                      | Only authorized voters can vote                                      | ✅ Provided — per-session registry enforced on-chain.                                                                                                                                                     |
| **Integrity of vote counting**             | Accepted votes are counted exactly once with the right weight        | ✅ Provided by contract logic (tested), assuming the chain itself is honest.                                                                                                                              |
| **Ballot confidentiality (secret ballot)** | Nobody can learn how a specific voter voted                          | ❌ **Not provided.** `VoteCast(sessionId, voter, optionIndex, weight)` is public. Running tallies can be reconstructed before closing even though `getResults` reverts until closure.                     |
| **Anonymity**                              | Votes cannot be linked to a real-world identity                      | ❌ **Not provided.** Addresses are pseudonymous, but the organizer's eligibility list maps them to people, and weights (share counts) can identify large shareholders. **Pseudonymity is not anonymity.** |
| **Receipt-freeness / coercion resistance** | A voter cannot prove their vote to a third party                     | ❌ Not provided — the transaction is a proof.                                                                                                                                                             |

**Data minimisation:** names, e-mails, passwords, descriptions and share registers are stored **only off-chain** in PostgreSQL. On-chain data is limited to: session title, option labels, times, quorum, organizer address, voter addresses, weights and votes. Organizers are warned in the UI not to put personal data in titles.

**Possible secret-ballot extensions (not implemented):** commit–reveal voting (hides choices until a reveal phase but not from the voter at reveal time), homomorphic tallying (e.g. ElGamal with threshold decryption), or zero-knowledge membership proofs (e.g. Semaphore-style nullifiers). Each needs careful cryptographic design, key ceremonies and audits; claiming privacy without them would be misleading.

## 3. Assets

| Asset                                      | Where                                                     | Why it matters                                      |
| ------------------------------------------ | --------------------------------------------------------- | --------------------------------------------------- |
| A1 Vote integrity (accepted votes, totals) | Contract storage/events                                   | Core value of the product                           |
| A2 Eligibility registry & weights          | Contract (authoritative) + DB (prepared list)             | Determines who decides and how much                 |
| A3 Role keys (admin, organizer wallets)    | User wallets (local test accounts here)                   | Control session lifecycle and organizer permissions |
| A4 User credentials & sessions             | DB (bcrypt hashes, SHA-256 token hashes), HttpOnly cookie | Account takeover                                    |
| A5 Personal data (synthetic)               | DB only                                                   | Privacy / legal exposure in a real deployment       |
| A6 Audit trail                             | Contract events, `AuditEvent`, `TransactionReference`     | Accountability                                      |
| A7 Availability of API, DB, node           | Infrastructure                                            | Votes cannot be cast during an outage               |
| A8 Secrets (DB password, env)              | `.env` (gitignored)                                       | Infrastructure compromise                           |

## 4. Attackers

| Attacker                          | Capabilities                                                                                          |
| --------------------------------- | ----------------------------------------------------------------------------------------------------- |
| T1 Outside attacker               | Internet access to the web app and API; can craft any HTTP request; no account                        |
| T2 Malicious shareholder          | Valid account and wallet; tries to vote twice, vote for others, see others' data, escalate privileges |
| T3 Malicious / careless organizer | Organizer role; may try to manipulate eligibility, cut voting short, or change rules                  |
| T4 Malicious administrator        | Admin role on-chain and off-chain; may try to fabricate results                                       |
| T5 Compromised backend / DB       | Full control of the API server or database                                                            |
| T6 Chain observer                 | Reads all public chain data                                                                           |
| T7 Malicious website              | Lures a logged-in user to a hostile page (CSRF)                                                       |

## 5. Threats, attack paths and mitigations

| 1   | **Broken access control**                         | T2 calls organizer/admin endpoints directly; T2 opens IDs of other orgs' elections                                   | H      | M          | Server-side RBAC from DB memberships (`services/access.ts`); per-org scoping; 404 for invisible resources; contract roles (`ORGANIZER_ROLE`, session organizer, admin)                                                                                                                      | `authorization.test.ts` (shareholder/auditor/admin cannot create; cross-org 404; non-owner cannot edit); contract tests "rejects … unauthorized" | Logic bugs in untested paths; no formal verification                                                                                                                                                                                                                     |

## 6. Local development key policy

1. Only Hardhat's built-in **public test accounts** on chain **31337** are used. Their keys are published by Hardhat and must be treated as compromised.
2. No private key appears in the repository, in `.env`, in the frontend bundle or in logs written by SecureVote.
3. `hardhat node` itself prints the test keys at startup. `npm run dev` redirects that output to `.run/hardhat-node.log` (gitignored). **Do not show it in screenshots or the demo video.**
4. Never import these accounts into a wallet that is connected to a public network; never send real funds to them.
5. The backend and frontend refuse other chain ids (`CHAIN_ID` must be 31337; the dev signer checks the node's chain id).
6. Before any real deployment: new keys generated on hardware wallets, admin role on a multisig, keys never on servers.

## 7. Audit limitations

- No external audit, penetration test, fuzzing (e.g. Echidna/Foundry invariants) or formal verification was performed.
- Static analysis is limited to solhint and TypeScript/ESLint. Slither was not run (Python tooling not set up in the build environment).
- Tests demonstrate intended behaviour for the listed cases; they cannot prove the absence of vulnerabilities.
- The threat model covers the prototype's architecture. A production design (multi-tenant hosting, real identity verification, public/consortium chain, key management) needs a new threat model.
